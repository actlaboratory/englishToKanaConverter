# 辞書編集方針: 部品語の読みと複合語の読みの一貫性

## 1. 背景・目的

[issue #5](https://github.com/actlaboratory/englishToKanaConverter/issues/5)は、「[issue #4](https://github.com/actlaboratory/englishToKanaConverter/issues/4)で議論されたような話題が今後も出てくる可能性が高いため、辞書の編集方針を明確にして文書化する」ことを求めている。issue #4は`where`・`when`等の`wh`の発音の扱いについての議論で、「英語の実際の発音に忠実であるべきか」と「聞き分けやすさ（他の語と区別できること）を優先すべきか」というトレードオフが論点になった。

本ドキュメントは、その論点が実際に辞書のどこに・どのくらい表れているかを`dictionaries/phrases.json`（約49,000件、[issue15-dictionary-json-format.md](./issue15-dictionary-json-format.md)参照）に対する調査によって特定し、方針を明文化したものである。対象読者は、辞書に新しい語を追加する開発者、および既存の読みの妥当性を判断する必要がある開発者を想定する。

機械的な整合性チェックだけでは洗い出せない表記ゆれもあるため、個々のエントリーを丁寧にレビューする作業を継続的に行い、見つかった不統一と、それに対する方針をこのドキュメントに随時追記していく。

変換アルゴリズム自体（どの辞書をどう参照するか）については[conversion-logic.md](./conversion-logic.md)を、辞書ファイルの形式的なルール（使用可能文字、最適化コマンド等）についてはREADME.mdの「辞書のメンテナンス」節を参照。本ドキュメントは、**個々の語の読みをどう決めるか（言語的な方針）**に焦点を当てる。

## 2. 調査方法

`phrases.json`の各エントリー（見出し語Kと読みR(K)）について、Kが「既に辞書に登録されている別の語」の組み合わせ（接頭辞＋基語、基語＋接尾辞、基語＋基語）として分解できる場合に、その組み合わせの読みを単純連結したものとR(K)を比較した。

* 接尾辞: `suffix.json`の8エントリー（`S`、`ES`、`D`、`ED`、`ING`、`LY`等）を使い、`K = 基語 + 接尾辞`となる基語が`phrases.json`に存在するケースを総当たりで比較。
* 接頭辞: `prefix.json`の2エントリー（`NO`、`UN`）に加え、辞書内で高頻度に現れる`IN`・`RE`・`DIS`についても同様に、`K = 接頭辞 + 基語`となる基語が`phrases.json`に存在するケースを比較。
* 複合語: 任意の分割点で`K = 語1 + 語2`となり、語1・語2の両方が独立して`phrases.json`に存在するケース（約2,400件）も比較したが、大半は`FORMAT`+`TING`のような偶然の文字列一致であり、有益な知見は得られなかった。

## 3. わかったこと

### 3.1 屈折語尾（-s/-ed/-ing/-ly）は概ね一貫しているが、`suffix.json`のフォールバックだけが乖離している

`基語+接尾辞`の単純連結とR(K)が一致しないケースは数千件見つかったが、内容を見るとその大半は英語として正しい音便変化だった。例えば`ABATED`は`アベイトゥ`+`ドゥ`＝`アベイトゥドゥ`ではなく、正しい有声化を反映した`アベイティドゥ`になっている。`ADDRESSES`も同様に、単純連結の`アドゥレスイズ`ではなく`アドゥレシズ`という、正しい有声化・音節構造を反映した読みになっている。

つまり、**既に登録されている約49,000件は、（表記上の単純連結ではなく）実際の英語の発音パターンに概ね忠実に統一されている**。

一方、この規則性を担保しているのは個々のエントリーそのものであり、`_partsToKana`が未登録語の救済に使う`suffix.json`（`D`→`ドゥ`、`S`→`ズ`等）は単純な文字列連結しか行わない。つまり、**似た語が数百〜数千件すでに登録されているにもかかわらず、たまたま未登録の新語だけは`suffix.json`由来の不自然な読みになる**、という構造的な不統一が存在する。

この点については、`suffix.json`に音便規則を持たせて根本的に解消することも考えられるが、対象になり得る語数が非常に多く（`-s`だけで2,900件超の「不一致」候補）、語末の音（有声/無声、破裂音か否か等）に応じた分岐が必要になるなど改修コストが大きい。一方で影響範囲は「基語は個別登録されているが、屈折形は未登録の語」という限定的なケースにとどまり、多くの場合は最終手段の`_alphaToSpell`（1文字ずつのスペルアウト）よりはましな近似が得られている。そのため、この乖離は既知の制約として許容し、`suffix.json`の改修は行わない（5章参照）。

### 3.2 否定接頭辞＋母音始まりの語で、同一の音韻環境なのに読みが3パターンに割れていた

これが本調査で見つかった最も明確な不統一である。`UN-`＋母音始まりの語（`UN`が実際に「否定」を意味する生産的な複合語に限る）を洗い出すと、同じ「UN+母音」という環境にもかかわらず、次の3パターンが混在していた（修正前）。

| パターン | 例（修正前） |
| --- | --- |
| A: ンを脱落させ直接リンク | `UNABLE`→`アネイブル`、`UNARM`→`アナーム`、`UNASHAMED`→`アナシェイムドゥ` |
| B: ンを保持しつつ余分な子音（ナ行等）を挿入してリンク | `UNAWARE`→`アンナウェアー`、`UNAMUSED`→`アンナミューズドゥ`、`UNAVAILABLE`→`アンナベイラブル` |
| C: ンを保持し、そのまま母音に接続 | `UNAVOIDABLE`→`アンアボイダブル`、`UNEXPECTED`→`アンエクスペクティドゥ` |

`IN-`でも同様の混在があり（例: `INEFFECTIVE`だけが`インニフェクティブ`とB型で、`INEFFICIENT`は`イネフィシェントゥ`とA型）、さらに`INEPTITUDE`→`ニネプティチュードゥ`のような単純な脱字と見られる例もあった。

なお、`prefix.json`のもう一方のエントリーである`NO-`も同じ方法で調べたが、こちらで見つかったのは母音接続時の脱落／同化という3.2節の問題とは別種の表記ゆれだった。`prefix.json`上の`NO`の読みは`ノー`だが、`NOBODY`→`ノウボディー`、`NOFOLLOW`→`ノウフォロウ`、`NOTABLE`→`ノウタブル`のように、多くのエントリーが`ノー`ではなく`ノウ`という長母音表記になっている。これは接頭辞と母音始まりの基語の結合方法の問題ではなく、長母音そのものの表記統一（`ー`か`ウ`か）という別の論点であるため、本ドキュメントでは扱わず、別途整理する。

参考として`RE-`接頭辞（約250件）も調べたが、`REACT`→`リアクトゥ`、`REASSEMBLE`→`リアセンブル`、`REORGANIZE`→`リオーガナイズ`のように、ほぼ全件が「接頭辞の読みをそのまま、余分な音を足さずに基語の読みへ接続する」形で統一されていた。ただし、これを「`UN-`/`IN-`でも同じように統一できる根拠」として扱うのは誤りである。`RE`は既に母音`イ`で終わる1モーラ（`リ`）であり、直後に母音が続いても読み方の選択肢自体が存在しない（`リ`+母音は常に`リ`+母音にしかなり得ない）。一方`UN`/`IN`の`N`は撥音（モーラ音素としての「ン」）であり、日本語の音韻として、直後に母音が続く場合に「ンのまま残す」か「ナ行などに同化する」かという**本当の意味での選択の余地**がある。3.2節で見つかった表記揺れは、この撥音特有の曖昧さに起因するものであり、`RE-`のように「母音接続に選択肢がない」環境が一貫していたことは、その曖昧さの解消策としては参考にならない。

この不統一の原因を、本リポジトリでの[Bilingual Emacspeak Projectの`bep-eng.dic`](http://www.argv.org/bep/)と[HISSの読み辞書](https://github.com/actlaboratory/HISS-dictionary)の統合に求めるのは正確ではない。HISS辞書由来でこのリポジトリに追加された語はそれほど多くなく、辞書の大部分は`bep-eng.dic`に由来する。`bep-eng.dic`自体が、GPL化される以前から長い歴史を持ち、複数のメンテナーの手を経て作られたデータである。撥音の実現方法という、そもそも複数の答えがあり得る箇所であるがゆえに、`bep-eng.dic`の成立過程で担当者ごとに異なる選択がなされたまま残った、というのが実態に近いと考えられる。より詳しい経緯を追う場合は、`bep-eng.dic`の元データを管理している[bep-argv/bep-ss](https://github.com/bep-argv/bep-ss)リポジトリも参考になる。

### 3.3 「語源的には接頭辞＋基語だが、現代英語では分割されない語」は対象外とすべき

上記の調査対象を`DIS-`＋母音にも広げたところ、`DISASTER`（`ディザスター`、基語`ASTER`＝`アースター`）や`DISEASE`（`ディジーズ`、基語`EASE`＝`イーズ`）が「不一致」として検出された。しかしこれらは語源的には`dis`+`aster`／`dis`+`ease`でも、現代英語の話者には分割不能な一つの単語として発音される（`disease`は`ディスイーズ`ではなく`ディジーズ`が正しい）。

このような語を無理に「接頭辞＋基語の直接連結」に合わせると、かえって誤った読みになる。したがって3.2節の方針は、**現代英語話者にも「否定＋既存の語」という構造が意味的・音声的に透けて見える生産的な複合語にのみ適用し、`DISEASE`・`DISASTER`や、`UNION`・`UNIQUE`・`UNIONIZE`（`uni-`＝「一つの」に由来し、否定の`un-`ではない）のような、たまたま同じ綴りで始まる別語源の語には適用しない**。

## 4. 決定した方針

### 4.1 否定接頭辞＋母音始まりの語: 「ンを保持し、余分な音を挿入せず基語の読みへ直接接続する」方式に統一する

3.2節のC型を既定の方針とする。前節の通りこれは`RE-`接頭辞の一貫性を根拠にした選択ではない。根拠は以下の通り。

* `prefix.json`の`UN`エントリーによる自動分解（後述）が実際に生成する読みと一致し、新規登録時に判断がぶれにくい。
* issue #4での`wh`の議論と同じく、否定を表す接頭辞（`アン`/`イン`）を構成する`ン`を保持したほうが、語の意味的な区切りが聞き取りやすい。ンを脱落させる（A型）と、否定の接頭辞が付いているかどうかが読み上げだけでは分かりにくくなる。
* B型（ンを保持しつつ子音を追加する）は、単純な連結ルールとして説明・再現がしにくい。

これを踏まえた具体的なルールは次の通り。

* `UN-`・`IN-`など子音で終わる否定接頭辞は、その接頭辞自体の読み（`UN`→`アン`、`IN`→`イン`）をそのまま使い、母音で始まる基語の読みへ直接連結する。基語の頭母音を消したり（3.2節のA型）、聞き取りやすさのために子音を追加で挿入したり（3.2節のB型）しない。
* 基語は、独立した単語として辞書に既に登録されている読みをそのまま使う。基語側の読みを複合語用に変更しない。
* 例: `UN`(`アン`)+`ABLE`(`エイブル`)=`UNABLE`→`アンエイブル`。`IN`(`イン`)+`ORGANIC`(`オーガニック`)=`INORGANIC`→`インオーガニック`。
* 適用対象は3.3節の条件（現代英語でも否定接頭辞＋独立した基語という構造が透けて見える生産的な複合語）を満たす語に限る。`DISEASE`型の融合語や、`UNION`型の別語源語は対象外。

なお、[prefix.jsonの`UN`エントリー](../englishToKanaConverter/dictionaries/prefix.json)を使った自動分解（`_partsToKana`）は、この方針に従うと実際に生成される読みと一致する。つまり`UN-`語であれば、この方針に従う限り`phrases.json`に個別登録しなくても自動分解だけで正しい読みが得られる。一方`IN`は`prefix.json`に登録されていない（登録されているのは`NO`・`UN`のみ）ため自動分解の対象にならず、`IN-`語は今後もこの方針に沿った読みを`phrases.json`に個別登録する必要がある。

この方針に基づき、3.2節で検出したA型・B型の実在する不統一エントリー33件（`UN-`16件、`IN-`17件。`UNARY`・`UNION`・`UNIONIZE`・`UNIONIZED`・`UNITS`・`INITS`は3.3節の理由により対象外とし据え置いた）を、本ドキュメントの追加と同じ変更でC型に修正済みである。

### 4.2 今後の新規登録時のチェック方法

新しく否定接頭辞＋母音始まりの語を登録する際は、次の手順で確認する。

1. その語が3.3節の条件（意味的に分割可能な生産的複合語）を満たすか確認する。満たさなければ、実際の発音に基づき自由に読みを決めてよい（4.1節の方式に従う必要はない）。
2. 満たす場合、接頭辞の読み（`UN`→`アン`、`IN`→`イン`等）と、基語の辞書登録済みの読みをそのまま連結した読みを採用する。
3. 連結した結果が明らかに不自然（実際にそう発音されない）と感じる場合は、個別に判断してよいが、その判断根拠をコミットメッセージ等に残し、同じ接頭辞の他のエントリーとの整合性を`tools/optimizeDic.py`実行前に確認する。

## 5. 許容することにした既知の不統一

3.1節で触れた`suffix.json`（`-s`/`-ed`/`-ing`/`-ly`等の未登録語向けフォールバック）の読みが、`phrases.json`内で実際に使われている音便パターンと乖離している問題は、**許容し、当面`suffix.json`の改修は行わない**方針とした。

* 影響範囲は「基語は個別登録されているが、当該の屈折形自体は未登録」という語に限られ、既に個別登録されている約49,000件の読みには影響しない。
* 語末の音（有声/無声、破裂音か否か等）に応じた分岐が必要になり、改修コストが対象語数（`-s`だけで2,900件超の「不一致」候補）に見合わない。
* この乖離が生じても、結果は最終手段の`_alphaToSpell`（1文字ずつのアルファベット読み上げ）よりは自然な近似になっており、実用上致命的ではない。

今後、この判断を覆すだけの実害（誤読による問い合わせの増加等）が確認された場合は、改めてissueを起票して再検討する。

## 6. `V`の文字の読み方: 基本的にバ行に統一する

否定接頭辞のケースとは別に、個々のエントリーを丁寧にレビューしていく中で見つかった不統一の1つ目として、`V`の文字（`ヴ`か、バ行`バ・ビ・ブ・ベ・ボ`か）の表記ゆれを扱う。今後も同様に、レビューで見つかった不統一をこの形式で追記していく。

### 6.1 調査で見つかったこと

見出し語に`V`を含むエントリーは`phrases.json`に約4,000件あるが、読みに`ヴ`（`ヴァ・ヴィ・ヴ・ヴェ・ヴォ`）が使われているのは1,147件にとどまり、大半はバ行で読まれている。単に少数派というだけでなく、**同一語族の中で`ヴ`とバ行が入り混じっている**ケースが多数見つかった。

| 語族 | 揺れの実例 |
| --- | --- |
| `GOVERN-` | `GOVERN`→`ガヴァン`／`GOVERNED`→`ガヴァンドゥ`／`GOVERNMENT`→`ガヴァメントゥ`に対し、`GOVERNANCE`→`ガバナンス`／`GOVERNMENTAL`→`ガバメンタル`／`GOVERNMENTS`→`ガバメンツ` |
| `-VOLVE` | `DEVOLVE`→`ディボルブ`／`EVOLVE`→`イボウルブ`／`INVOLVE`→`インボルブ`／`REVOLVE`→`リボルブ`（`ヴ`なし）に対し、`CONVOLVE`→`コンヴォルヴ`／`REVOLVER`→`リヴォルヴァー`（`ヴ`が2つ） |
| `CONSERVE` | `CONSERVE`→`コンサーブ`（`ヴ`なし）に対し、同じ語の活用形`CONSERVED`→`コンサーヴドゥ`／`CONSERVING`→`コンサーヴィング`（`ヴ`あり） |
| `ADVISE` | `ADVISE`→`アドゥバイズ`／`ADVISER`→`アドゥバイザー`に対し、`ADVISEE`→`アドゥヴァイジー`／`ADVISES`→`アドゥヴァイジズ` |
| `TRAVELER`/`TRAVELLER` | 米式`TRAVELER`→`トゥラベラー`に対し、英式`TRAVELLER`→`トゥラヴェラー`（綴りの違いだけで表記が変わっている） |
| `VIRUS` | `VIRUS`→`バイルス`（独語風）、`ANTIVIRUS`→`アンティウイルス`（和製慣用語）、`CYTOMEGALOVIRUS`→`サイトゥメガロヴァイラス`（英語風）と3通りが混在 |

一方、`DEVELOP`系・`COVER`系・`VOKE`系（`CONVOKE`/`EVOKE`/`INVOKE`/`PROVOKE`/`REVOKE`）は語族内で完全に統一されており、バ行での統一自体は現実的に可能であることが分かる。

### 6.2 決定した方針

`V`の文字は、**基本的にバ行（`バ・ビ・ブ・ベ・ボ`）で読む**ことを既定の方針とする。`ヴ`は原則として使わない。

* 辞書の多数派が既にこの方式で統一されており、バ行を既定にすることで修正が必要な範囲（少数派の`ヴ`表記側）を最小化できる。
* `VIRUS`（`ウイルス`）のように、日本語の慣用読みとして定着している別形がある語は、この方針の対象外とし、慣用読みを優先してよい。
* `B`と`V`の聞き分けが必要になる特殊な文脈が将来的に見つかった場合は、個別に例外として判断し、その理由をコミットメッセージに残す。

### 6.3 今後の扱い

対象は見出し語に`V`を含む約4,000件（うち`ヴ`表記になっているもの約1,147件が主な修正候補）と、UN-/IN-のとき（33件）より一桁規模が大きい。今回はこの方針の文書化にとどめ、既存エントリーの実際の修正は別タスクとして改めて行う。
